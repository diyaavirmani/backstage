# Architecture

## System boundaries

```text
Next.js web app
  ├── event brief and host experiences
  ├── server-side agent workflow
  │     └── Sanity Context MCP → Sanity Knowledge Base
  └── operational API → booking and availability database
```

The Studio schema, reviewed local source catalogue, idempotent import command, and Context retrieval check are in place. Organizer discovery uses the configured Knowledge Base-only MCP endpoint at request time. `/venues` server-renders eligible published Sanity venue records; when Sanity is unavailable it clearly labels the checked-in JSON as a local preview.

## Frontend

The Next.js App Router serves the landing, organizer, host, venue catalogue, and embedded Studio routes. The organizer event brief remains a client component and retains its browser-local draft behavior. The `/venues` server page queries published records with `perspective: "published"`, limited to eligible `research-lead` venues with demonstration records excluded. It resolves source references, claims, spaces, resources, and policies on the server. The client component receives only catalog content needed to render city filters, source links, qualifications, and original source-check dates. The fallback origin is labeled, never represented as a successful live connection.

Shared TypeScript types in `src/types` define event briefs, venue knowledge, sources, hosting opportunities, match explanations, booking requests, resources, and checklist items before backend implementation begins.

## Sanity content and Knowledge Base

Sanity schemas model venues and host organizations, venue spaces, equipment/shared resources, hosting policies, hosting opportunities, claims, and source references. Claims include values, evidence type, citations, and checked dates; capacity records require a named space and layout. The seed data separates public documentation and historical events, explicitly marks unknowns, and sets the sample venues as research leads. Stable IDs and `createIfNotExists` imports preserve existing host-edited documents. The Knowledge Base query is documented in `docs/sanity-setup.md` and excludes demonstrations and all operational/user data.

## Agent retrieval

`POST /api/venue-discovery` lazily initializes the OpenAI provider and validates the stored event brief plus bounded user/assistant conversation history. It fetches the current published, research-only venue records from Sanity with a server-side project token. A request-scoped MCP client requires `initial_context` and `knowledge_base_read`, discovers paths from the current outline, and gives the model a tool that can read only those discovered paths. The call has input, read-count, deadline, and cancellation bounds and always closes the MCP client.

The model selects potential leads and paths from the current outline. It cannot return citation URLs or requirement classifications. The server limits the outline menu to the brief city and any explicitly requested venue/locality, then checks exact venue/locality identity, entry path, source IDs, and original URLs before publishing a card. Invalid model candidates are dropped. Requirement coverage comes from published, source-linked structured claims: audience eligibility is supported only when the organizer audience matches the documented condition; a requested room or equipment count needs count-specific evidence; explicit prohibitions can contradict a requirement; conflicting evidence stays unknown. Capacity can be supported only with a known guest count tied to a named room and layout, with enough capacity. Citation links are constructed from verified Sanity records, never from model output. Historical event evidence, Shifu’s access qualification, and distinct Ofis locations are preserved. The route writes sanitized verification metadata (entry paths, source IDs, and counts by requirement status) to server logs; it does not log event briefs, organizer requirement text, or credentials. Neither MCP retrieval nor this agent checks availability, confirms exact prices, or authorizes Backstage booking.

Provider setup is isolated in `src/lib/ai-provider.ts`. It reads server-only `OPENAI_API_KEY` and optional `OPENAI_MODEL` only when discovery is requested; the latter defaults to `gpt-4.1-mini`, so production builds do not require an OpenAI secret. Client-supplied system/tool/citation fields are rejected. Organizer conversation history is bounded and treated as untrusted reference material. A recommendation card can publish an explicit, one-time browser handoff containing its venue ID, exact discovery brief, unresolved coverage questions, and qualifications. The operations workspace resolves the stable venue ID against its server-provided venue list instead of requiring another choice. Saving a research draft resolves the selected venue and its source/claim references again using the project-scoped server token; browser-supplied citations or authority fields are ignored. The store records the trusted evidence snapshot and capture time alongside the original source-check dates and discovery brief. A required review control applies before a research draft can be saved. Research submission is rejected server-side. Live OpenAI and Sanity verification is recorded in [the build log](build-log.md).

## Operational booking backend (Milestone 4)

Sanity remains the read-only venue knowledge layer. A separate Node server-side SQLite store owns application drafts, immutable brief snapshots at approval, resources, dated released availability, internal blocks, holds, reservations, checklist tasks/history, and status transitions. Migrations are in `db/migrations`; initialization is lazy and occurs only from `/api/operations`, so a build does not need a database. `BACKSTAGE_DB_PATH` selects the file path and defaults to ignored `.data/backstage.sqlite`.

The API issues an opaque random HTTP-only, SameSite=Lax cookie. The database stores its SHA-256 hash and a workspace/organizer-or-host simulation role. Every query and mutation is scoped to that server-resolved workspace; client-provided record IDs never provide access by themselves. The role selector is plainly labelled simulation and does not authenticate a real organizer or host. Communications remain in the app.

Each workspace contains six source-backed research leads and two clearly fictional hosts, one per city. Research leads permit saved private application drafts with an exact discovery brief snapshot, server-resolved Sanity claims/sources, citations, evidence-capture time, and unanswered questions; the API rejects submission because no Backstage booking authority is established. Only fictional demo venues can enter the request queue. Their access model (sponsored or pro bono) is a separate database field from host approval fulfillment. Their rooms carry capacity tied to a named layout; finite equipment has stable resource IDs and quantities. All sample locations, policies, availability, requests, calendars, and confirmations are labelled fictional and exist only in this operational database. The Sanity seed/query path contains only its published research catalogue and never reads the demo inventory.

Application state transitions and allocations use SQLite `BEGIN IMMEDIATE` transactions. Approval checks event type and essential conditions, selected room capacity/layout, required rooms/equipment quantities, internal blocks, released availability, and other active allocations. Candidate intervals include event setup and cleanup. Overlap uses half-open boundaries, so adjacent occupied intervals are allowed. The database counts finite shared equipment units, expires holds before displaying the calendar and ignores expired holds during allocation, and releases allocations on rejection/cancellation. An alternative must fit organizer-captured date/time flexibility and current host availability; it is not allocated until the organizer explicitly accepts and the host later approves. Approval records the accepted brief snapshot and inserts the checklist idempotently. Time values are stored as UTC ISO timestamps and displayed in Asia/Kolkata.

The current implementation uses Node's built-in synchronous `node:sqlite` `DatabaseSync` (no native npm dependency) and Node 26.9. Node documents this API as a release candidate, so upgrades should be checked against its [current SQLite API status and version history](https://nodejs.org/api/sqlite.html). Synchronous SQLite and a file are suitable for this single-node demonstration, not a multi-instance production deployment. Production needs a managed durable database (or a deliberately single-node durable-volume deployment), backup/restore, connection/latency monitoring, rate limits, account authentication, role authorization, and cross-origin/abuse controls. A host must onboard and verify its own actual rules and availability before any real request can be represented as bookable.

## Environment configuration

`.env.example` contains placeholder project/dataset identifiers and server-only import, Context, and OpenAI values. The public site, local preview, and production build work without credentials, while agent requests return an actionable configuration error if required secrets are absent. `.env.local` is ignored. Project data reads use `SANITY_PROJECT_IMPORT_TOKEN`; Context reads use the separate organization `SANITY_ORGANIZATION_TOKEN`; model calls use `OPENAI_API_KEY`. None are exposed to browser code.
